# RAG 与 MCP 设计

## 1. 为什么不能全部走 RAG

金融数据的生命周期差异很大。

适合进入 RAG 的内容通常是：

- 历史新闻；
- 产业链资料；
- 长期研究材料；
- 事件背景；
- 需要被反复引用的文本知识。

而以下内容不适合提前向量化后长期保存为“最新事实”：

- 实时行情；
- 日/分钟 K 线；
- 资金流；
- 龙虎榜；
- 融资融券；
- 动态财务和估值数据；
- 历史 PE/PB 区间的最新计算结果。

这些数据变化快，因此由 AShare MCP 在推理阶段动态获取。

---

## 2. RAG 链路

公开版概念流程：

```text
资讯采集
  ↓
Backblaze B2 保存原文
  ↓
Supabase 保存元数据 / 摘要 / 索引
  ↓
Embedding 向量召回
  ↓
Qwen3-Reranker 重排序（在启用精排的检索节点）
  ↓
Top-K 上下文筛选
  ↓
提供给 LLM / Deep Research
```

这里的 Top-K 不是新的检索算法，而是：

> 在召回和重排序之后，只选择相关性最高的前 K 条作为上下文。

这样可以控制上下文长度，并减少低相关信息对模型判断的干扰。

---

## 3. 为什么需要 Reranker

Embedding 更适合做快速召回，但初步相似度不一定等于最终任务相关性。

因此在部分关键检索节点中增加 Qwen3-Reranker：

```text
大量候选材料
   ↓
Embedding 快速召回
   ↓
Reranker 再次判断 query 与候选材料的相关性
   ↓
重新排序
   ↓
Top-K

## 4. MCP 在系统里做什么

AShare MCP 把金融数据能力封装成 Agent 可调用的工具。

典型能力包括：

- 个股基本信息；
- 实时行情；
- 日线 / 分钟 K 线；
- 技术分析；
- 技术情绪分析；
- 财务数据；
- 公告 / 研报；
- 个股资金流；
- 龙虎榜；
- 融资融券；
- 历史 PE/PB 等估值信息。

模型不需要提前记住这些数据，而是根据任务主动决定是否调用工具。

---

## 5. 混合上下文

最终交给模型的不只是单一知识库结果，而是：

```text
用户问题
+ 自选股上下文
+ Investment Thesis Memory
+ RAG 历史知识
+ MCP 实时金融数据
+ 本轮 Deep Research 已累积证据

## 6. 产品层面的取舍

RAG 和 MCP 并不是“技术越多越好”。

真正的设计判断是：

> **什么信息应该被长期记住，什么信息应该在需要时实时获取。**

这能减少过期信息进入模型上下文，也让研究结果更容易追溯到具体证据来源。
