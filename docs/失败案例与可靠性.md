# 失败案例与可靠性设计

StockPilot 的稳定性设计不是一开始就全部想好的，而是由真实运行中的失败逐步推动出来的。

---

## 1. RSS 单源失效

### 问题

资讯采集依赖多个 RSS / 热点源，单个源超时、格式异常或暂时不可访问是常见情况。

如果采用“任一源失败就终止”的方式，整个晨报会非常脆弱。

### 调整

采用失败隔离：

```text
RSS 1 ✓
RSS 2 ✓
RSS 3 ✗ → 记录错误并跳过
RSS 4 ✓
...
```

原则：

> 单源失败不等于整体失败。

---

## 2. 定时任务偶发延迟

### 问题

GitHub Actions 定时触发并不适合被理解成“绝对准点”。

### 调整

增加主触发与 fallback 设计：

```text
Primary
  ↓
正常执行

Fallback
  ↓
仅在当天任务未完成时补救
```

这要求同时存在业务状态控制，否则会造成重复晨报。

---

## 3. 重复触发与幂等

### 问题

同一天可能因为人工重跑、fallback 或任务重试而触发多次。

如果每次都直接推送，用户会收到重复晨报。

### 调整

用业务状态表达发送过程，例如：

```text
READY → SENDING → SENT / UNKNOWN
```

只有满足预期状态的任务才可以获得发送权。

核心目标不是“发送以后再去重”，而是：

> 在业务层阻止同一任务被重复执行。

---

## 4. HTTP 200 但业务侧未真正接受

### 问题

曾出现过网络请求返回 HTTP 200，但用户端没有得到预期消息的情况。

这说明：

```text
HTTP 请求成功
≠
微信业务接口接受
≠
用户设备真正收到
```

### 调整

发送链路不能只检查 HTTP 状态，还要进一步检查业务响应，并单独记录业务侧接受状态。

公开作品集不会声称系统能够证明“设备 100% 收到”，而是强调：

> 不再把网络层成功直接等同于业务完成。

---

## 5. Dify / Agent 长链路超时

### 问题

复杂 Agent、Loop、工具调用越多，延迟和失败点也越多。

### 调整

按任务复杂度进行分流：

```text
简单事实 → MCP
历史解释 → RAG
复杂研究 → Deep Research
```

这样简单问题不需要承担 Deep Research 的全部时延与风险。

---

## 6. Structured Output 格式漂移

### 问题

主分析模型同时负责复杂推理和严格 JSON 时，容易出现：

- 字段缺失；
- 输出多余解释；
- JSON 结构漂移；
- Dify Loop 无法读取变量。

### 调整

将研究逻辑和格式化拆成不同节点：

```text
Planner：负责想清楚
↓
结构化节点：负责输出固定 Schema
↓
Loop：只消费稳定字段
```

---

## 7. 可靠性设计的产品意义

这个项目里最重要的一条经验是：

> **程序或模型“运行成功”，不等于用户任务“成功完成”。**

因此稳定性不只看：

- 是否报异常；
- HTTP 是否 200；
- LLM 是否返回文本。

还需要进一步看：

- 是否拿到有效数据；
- 是否重复执行；
- 是否进入正确任务路径；
- 是否保留证据状态；
- 是否真的到达业务侧接受状态。
