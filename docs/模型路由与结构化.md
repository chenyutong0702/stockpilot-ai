# 模型路由与结构化输出

## 1. 为什么不使用单一模型

不同节点对模型能力的要求不同：

- 金融资讯理解更看重领域语义与效率；
- Deep Research 更看重长上下文、复杂推理与工具使用；
- JSON Schema 转换更看重稳定、低成本、格式一致；
- 晨报最终编辑更看重信息压缩和微信阅读体验。

因此 StockPilot 不把所有任务交给一个“万能模型”。

## 2. 当前模型分工

### Ling 3.0 Flash Fin

主要用于：

- 金融新闻整理；
- 资讯理解；
- 日常金融分析；
- 对晨报输入材料进行高密度压缩。

### LongCat-2.0 / GLM

作为复杂推理、长文本研究和 Agent 节点的候选模型，根据工作流稳定性和成本进行替换。

### gpt-oss-120b

主要承担低成本结构化或最终整理类任务，例如：

- 固定字段输出；
- JSON Schema 转换；
- 中间结果整理；
- 晨报最终编辑。

## 3. “推理”和“格式化”为什么要拆开

早期尝试让主分析模型同时完成：

```text
复杂金融判断
+
严格 JSON 输出
```

实际会出现：

- 字段遗漏；
- JSON 格式漂移；
- 多输出解释文字；
- Loop 无法读取下游变量；
- 为了守格式反而削弱研究质量。

因此拆成：

```text
Research Planner
负责：研究逻辑与任务设计
       ↓
结构化中间层
负责：把任务转换成固定 Schema
       ↓
Research Loop
负责：消费结构化任务
```

核心设计原则：

> **强模型负责“想清楚”，结构化节点负责“说规范”。**

---

## 4. Agent 分流

模型路由不仅是“换模型”，也包括不同问题进入不同工作流。

```text
用户问题
  ↓
任务判断
  ├─ 行情 / K线 / 估值事实 → MCP 快速链路
  ├─ 历史背景 / 新闻解释 → RAG + 轻量分析
  └─ 多维开放问题 → Deep Research
```

这样可以避免：

- 查一个股价也跑 5 分钟研究；
- 所有任务都消耗高成本模型；
- 简单任务经过过长链路增加失败概率。

---

## 5. Prompt Engineering 在这里做什么

Prompt 不是简单“帮我分析股票”，而是负责定义 Agent 的行为边界，例如：

- Planner 不能直接给最终投资结论；
- 必须同时考虑支持逻辑与反向逻辑；
- 必须指出缺失证据；
- 需要按任务类型选择 MCP / RAG；
- 同源转载不能计为独立验证；
- 事实、市场观点和模型推断必须区分；
- 获取足够证据后停止继续 Tool Calling；
- 微信输出采用短段落而非复杂大表格。

因此可以理解为：

> **Tool Calling 决定模型能调用什么，Prompt Engineering 规定模型什么时候调用、怎么使用结果以及如何输出。**
